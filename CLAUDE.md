## Building

C++ bots build to `bot.wasm` via `cmake/CMakeLists.txt`, which requires `BOT_DIR` (bot directory containing `src/`), `BC_SDK` (the `sdk/` directory) and `WASI_SDK_PREFIX` (a wasi-sdk install, used with its CMake toolchain). It globs `${BOT_DIR}/src/*.cpp`, so new `.cpp` files are picked up automatically. Required flags (already set): C++20, `-msimd128`, and Wasm exnref exceptions (`-fwasm-exceptions -mllvm -wasm-use-legacy-eh=false`, linked against the wasi-sdk `eh` sysroot + `-lunwind`) — the runner's Wasmtime only supports that exception proposal, so don't change these.

`.vscode/settings.json` points CMake Tools at `cmake/`. Each C++ bot's `.clangd` reads `compile_commands.json` from the bot directory.

Python bots need no build; `pyrightconfig.json` adds `../../sdk/python` to the path for type checking.

### `cambc` CLI

Installed as a pip package. On Windows the executable is at `C:\Users\visvi\AppData\Local\Programs\Python\Python313\Scripts\cambc.exe` (not on PATH — `cambc add-to-path` fixes that per session); on macOS it is installed with `uv tool install cambc` at `~/.local/bin/cambc`. Run `cambc <cmd> --help` for options.

- `cambc run <BOT_A> <BOT_B> --map <name> [--rounds N] [-o DIR] [--statistics out.json] [--view]` — play a match. Bots are directory paths (e.g. `bots/starter-cpp`); maps resolve by bare name under `maps/`. `--rounds` truncates the game.
- `cambc build <BOT>` — compile a bot to Wasm. `cambc view [replay]` opens the visualiser.
- `cambc new`, `cambc maps pull` (refresh the map pool), `cambc init` (refresh `sdk/`), `cambc submit` / `cambc bundle`.

The replay bundle (`*.repl26a`) is a ZIP: `team-a.stdout` / `team-b.stdout` hold bot prints, `team-*.debug` the debug draws. Printing from a bot and reading `team-a.stdout` is the easiest way to inspect engine state, e.g. map layout (the `.map26a` format is binary; `game_map.camp_groups()` is empty during the draft, so dump on the first game turn). Bot prints that run out of fuel resume next turn, so give such runs a few rounds.

### Testing and tuning (`tools/*.py`, stdlib Python, parallel)

- `python3 tools/batch.py [memberA memberB] --games N` — exact-size sets; omit names for a newest-member round robin. Highest numbered version per member is selected, plain `vN` preferred to same-number suffix branches. Results use member names and save reports, JSON/CSV, logs, and replays under `matches/`. Swaps sides; normal fuel only. Reports Beta(1,1)-prior `P(win rate > 50%)` using distinct completed map/side setups so identical deterministic repeats do not inflate evidence. See `docs/BatchTesting.md`; tests: `python3 -m unittest discover -s tools -p test_batch.py`.

The engine is deterministic: one map + side = one game. For bigger samples, `arena.py --seeds N` plays random-draft games. Bots whose `draft.cpp` includes `experiment_seed.h` (Daniel v11 on) get the seed at compile time: `arena.seeded()` builds a copy per seed under `bots/_seeded/`, and it plays at the real 100k fuel. Older bots fall back to a fuel quantum of `1,000,000 + 10,000 * seed` (`arena.seed_fuel`), which hides opponents' fuel limits. Every arena game runs `--release`, as the platform does. Port the hook into each new version.

- `python3 tools/gate.py <candidate> <base> [--mode gain|nonreg|map] [--maps ...]` — **the gate for bot changes.** Side-swapped game pairs and a sequential probability ratio test (Fishtest-style, ±2.94). Batches of fresh draft seeds run until it decides: exit 0 pass, 1 fail, 2 inconclusive, 3 crashes. `gain` tests 50% vs 55%, `nonreg` 45% vs 50%, `map` 50% vs 65% for targeted fixes; pair `map` with an all-map `nonreg`. v10 vs v9 passed in 80 games.
- `python3 tools/scrim.py panel|sync|report|quota|create` — unranked scrims via `cambc match-groups` (T9). `panel` queues a fixed set for the live bot: 6 opponents (5 near our rating that beat us in ranked, plus the #1 team) × 2 groups of 5 of our worst maps, sides swapped; 60 games per version, so versions compare without ranked matchmaking variance. `sync` downloads finished groups into `data/scrims/<version>/` (summaries, feature rows, replay reports); `report` prints W-L per version, opponent and map. Quota: 50 groups (5 games each), rolling one hour from the first use, shared with teammates. Scrims play only our submitted bot.
- `python3 tools/ladder.py snapshot|versions|submitted <bot> --time <ISO>` — append our ladder rank and rating to `docs/ladder_history.csv`, and log each `cambc submit` in `docs/submissions.jsonl` (ranked listings don't say which submission played). Run `submitted` after every submission.
- `python3 tools/arena.py <botA> <botB> [--seeds N] [--min-winrate X]` — every map, both sides (plus N random-draft games per map and side); prints per-map results and A's win rate with a 95% interval. Use it as the regression gate before freezing a version. Bots are names under `bots/` or a teammate folder (first match in `bots/*/`, so `v5` means `bots/daniel/v5`; pass a path for `bots/simon/v5`). Works with cambc ≥ 2.2 (`--json` statistics, normalised by `arena.normalize`).
- `python3 tools/tune.py --bot v5 --params a,b,c [--iterations N --seeds S]` — evolution strategy over named constants (`name = 1.5f` in `src/bot.cpp`): builds copies under `bots/_tune*` (gitignored), plays each candidate against the incumbent, and accepts at ≥56%. Prints the best values; `--apply` writes them back. Always confirm the result with a large `arena.py --seeds` run, because single accepted steps can be noise.
- `python3 tools/scout.py --top 20 --matches 100 --summaries 20 [--replays N --maps a,b]` — read-only tally of the top ladder teams' drafts and builds (works for any team's games). Appends a feature row per game to `data/scout/features.jsonl`. `--replays` downloads and decodes their replays into `data/scout/replays/` (report, stats, gzipped timeline). `analyze.mjs` labels team A as "us" there.
- `python3 tools/benchmark.py replays/daniel-v9/features.jsonl` — per-map gaps between our feature rows and the top teams': gems at rounds 250/500/1000, gold, deaths, camp clears, first clear, as z-scores.
- `python3 tools/winmodel.py [--ours replays/<version>]` — win-probability model, a stdlib logistic regression on team differences every 100 rounds. It trains on every full summary we hold (ours plus `data/scout/summaries/`, which the scout fills). It prints accuracy per phase, each feature's value in submitted gems (e.g. 1 death ≈ −6 to −9 gems), and with `--ours` the round each of our losses was decided.
- `python3 tools/race.py <base> <variant>...` — successive halving: 3–6 variants of one change against the base on fresh seeds, dropping the worse half each round. Confirm the winner with `gate.py`.
- `python3 tools/gauntlet.py [--add <bot>]` — round-robin over the local pool (v7–v10, Jame v3, Simon v6, hunter-v0), results cached in `data/gauntlet/`. Batch Bradley–Terry ratings (v8 = 0) with bootstrap intervals, and a straight-line mapping to the ladder from the submitted versions.
- `python3 tools/meta.py > docs/research/top-team-meta.md` — the top teams' draft rates by team size, emblem build order and shard mix, from scouted summaries.
- `python3 tools/openings.py <map>... --ours replays/<v>...` — camp-clear order and timing (round, group id, rewards) of the top teams' games and ours; findings in `docs/research/top-team-play.md`.
- `python3 tools/styles.py replays/daniel-v8 replays/daniel-v9 ...` — k-means grouping of our ranked opponents (draft, shard mix, kills, gem lead) with our win rate against each group.
- `python3 tools/draft_lab.py collect --bot <bot>` / `fit --no-write` — random-roster self-play, then per-team-size champion values (Bradley–Terry plus gem-margin ridge). Findings: `docs/research/drafting.md`.

### Replay analysis

`python3 tools/ranked.py replays/<version> --since <submission ISO time> --replays losses` (cambc ≥ 3, logged in) is the way to get ranked data; don't download replays from the website. It is incremental: `matches.json` accumulates every match seen and listing stops at the first page with nothing new, so re-run it as often as you like. Summaries (`cambc matches summary --json`, same schema as `--statistics`, kept in full and gzipped as `summaries/<id>.json.gz`, ~70 kB; older ones are stripped `.json`) and replays download 8 at a time (`--jobs`; one summary ~2 s, one replay ~8 s, no rate limiting seen). Each selected replay is analysed into `<dir>/analysis/<match id>.txt` (+ `.stats.json`) and deleted; a match with a report is never re-downloaded, and a failed one is retried on the next run. Ranked listings do not say which submission played, so separate versions by `--since` (the submission time) and one folder per version. Each game also gets a row in `<dir>/features.jsonl` (`tools/features.py`: deaths by killer, camp clears, fuel exhaustion, shards bought, gems at rounds 250/500/1000, and loss signatures: frozen, tiebreak, race, spiral, camp_trap, fuel, fault). It prints the record, every game per map, and a table of loss signatures per map. `cambc match-groups create` queues five unranked matches against a chosen team.

`python3 tools/auto.py --base v8 --candidate <name> [--skip-tune] [--submit]` runs one unattended cycle: `ranked.py --replays losses` into `replays/daniel-<base>`, copy base to `bots/daniel/<candidate>` (kept if it exists, so hand edits survive), `tune.py --apply` on v8's main constants, `arena.py` gate vs base (`--gate 0.55`, `--seeds 4`), and `cambc submit` only with `--submit` and a passing gate. Logs go to `data/auto/`. It never commits. `cambc match-groups create` queues five unranked matches against a chosen team.


`node tools/replay/analyze.mjs [--us A|B] [--out dir] <replay.zip|.repl26a|dir>...` decodes replays (engine 0.0.x to 2.0.0, i.e. SDK 4.0; layouts are picked by the wasm's snapshot size) with the visualiser's own engine wasm (found under `%LOCALAPPDATA%/cambc/assets` on Windows, `~/Library/Caches/cambc/assets` on macOS). It works on platform downloads (zip: `replay.repl26a` + our stdout) and on local bundles. For each input it writes `<name>.stats.json` (same schema as `--statistics`) and `<name>.timeline.csv` (per champion per round: position, health, alive, gems, gold, K/D/A), and prints a report: score over time, per-champion table with builds, and every death with position and gems lost. Our team is detected from the draft log lines. It exits 1 if any input fails to decode (ranked.py then keeps no report and retries next run). Timeline rows are sampled at the start of each round, so a death's position can be one tile off the summary's. The visualiser's own CSV export only covers rounds already played back, so don't rely on it. Platform replays go in `replays/<version>/` (gitignored); write analysis to `replays/<version>/analysis/`.

The installed CLI may be newer than the vendored `sdk/` (it warns and suggests `cambc init`).

## Bot architecture

Every bot runs the same loop in `main`: forever, if `is_draft()` run the draft logic, else run the champion turn; catch and log any exception; then `end_turn()`. An exception must never escape the loop, or the bot dies.

- **One bot instance per champion.** Each champion runs its own copy of the program, keeping state across turns in process memory (e.g. `Bot` members). Teammates don't share vision or memory; cross-champion communication is only via:
  - `draft_memory` — 1024 bytes written during the draft, read-only during the match.
  - `shared_memory` — 8 bytes per team, read/write all match (starter stores a little-endian u32 at offset 0).
- **Draft phase** (`draft.cpp` / `draft.py`): full map visible, 10x fuel on the first draft turn; picks champions one at a time, simultaneously with the opponent. A missing pick is randomised.
- **Fuel, not time**, limits compute: 100k/turn for C++/Rust, 5x for OCaml, 25x for Python; 2x on the first game turn. Running out suspends the bot mid-execution and it *resumes from that point next turn* — so expensive work can silently span turns.
- **Fuel costs hide in SDK calls.** Every engine call costs roughly 150 fuel. `vision::camp_at`, `vision::camps()` and `map::camp`/`camp_groups()` reload *every* camp group from the engine (~30k fuel per call on a 70×70 map), so in a turn use the cached lookup in `bots/simon/v4/src/world.h` instead. Running out of fuel never shows up as an error; the turn just stops and resumes next round, so measure with `cambc::fuel_remaining()`.
- **Camp spawn tiles:** an occupied spawn tile delays the whole group's respawn. Never wait on one.
- **Lean on SDK bitboards.** Map/vision queries return `bitboard`s (`map::walls()`, `vision::camp_tiles()`, …) combined with `| & ~`; pathfinding uses `distance_field::compute_to` and `bitboard::reachable_tiles`. The rules recommend using the SDK's movement mask rather than recomputing walkability.
- **Actions can return `false` without throwing** when a hidden unit (e.g. in a bush) blocks the destination; that doesn't consume the allowance, so retry elsewhere. Acting on a *known* invalid target throws (`cambc::error` / Python `cambc.Error`).
- Python API mirrors C++: C++ namespaces → submodules (`cambc.game_map`, `cambc.vision`, `cambc.draft`, …), `cambc::self()` → `cambc.me()`, overloads → optional params, enums are `UPPER_CASE`.

## Game rules worth keeping in mind

See `docs/GameRules.md` for detail. Win by tributing 1000 gems (or most gems at round 2000; tiebreaks: lifetime gold, kills, then Team B). Loop: kill every monster in a cardinally-connected camp group → stand on its spawn tiles uncontested for 5 rounds to capture → carry gems to an altar (Chebyshev ≤ 1) and channel a tribute of `max(1, ceil(gems/10))` turns. Carried gems are lost on death (to the killer, or destroyed by camps). Ranged champions can't move and basic-attack in the same turn; melee can. Gold buys shards (30g; 5 of a kind → emblem) and consumables (10g) on spawn or while dead.
